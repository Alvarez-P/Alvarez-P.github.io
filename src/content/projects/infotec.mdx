## Contexto y problema

CFE TEIT es la división de telecomunicaciones de la Comisión Federal de Electricidad, responsable de operar infraestructura crítica de comunicaciones a nivel nacional. La plataforma existente enfrentaba desafíos de escalabilidad y mantenibilidad: un monolito con acoplamiento entre módulos de negocio que dificultaba tanto la evolución independiente de funcionalidades como la incorporación de nuevos requerimientos regulatorios y operativos.

El problema central era doble: por un lado, la **complejidad del dominio de telecomunicaciones** — gestión de torres, cobertura geográfica, rutas de fibra óptica, monitoreo de red, y asignación de recursos — requería un modelo de dominio rico que el monolito no podía expresar adecuadamente. Por otro lado, la **criticidad del sistema** (operaciones nacionales en producción) demandaba una arquitectura que permitiera desplegar cambios con confianza sin arriesgar la estabilidad general.

El reto: diseñar y liderar la migración hacia una arquitectura basada en microservicios sin interrumpir la operación existente, mientras se construían nuevos módulos desde cero con patrones sostenibles.

## Decisiones de arquitectura

### Domain-Driven Design desde el inicio

Elegimos DDD porque el dominio de telecomunicaciones tiene una complejidad inherente que no podíamos modelar con CRUD. Las sesiones de *Event Storming* con operadores y administradores de CFE nos permitieron descubrir un *Ubiquitous Language* compartido: conceptos como "enlace", "cobertura", "torre", "segmento de red" dejaron de ser tablas y se convirtieron en **Aggregates** con reglas de negocio explícitas. Este lenguaje común fue el puente entre el equipo técnico y los expertos de dominio, eliminando ambigüedades que antes generaban bugs en producción.

### Clean Architecture en NestJS

Cada microservicio sigue Clean Architecture con cuatro capas:

- **Domain**: Entidades, *Value Objects*, eventos de dominio. Sin dependencias externas.
- **Application**: Casos de uso, puertos (interfaces de repositorio), DTOs.
- **Infrastructure**: Implementaciones concretas (Prisma, transporte gRPC, caché).
- **Presentation**: Controladores REST, WebSocket, middleware de autenticación.

La regla de dependencia (*The Dependency Rule*) se respeta estrictamente: el código de dominio no sabe que existe Prisma, ni NestJS, ni siquiera HTTP. Esto nos permitió probar la lógica de negocio en aislamiento total y reemplazar implementaciones de infraestructura sin tocar una línea de dominio.

### PostGIS para datos geoespaciales

La infraestructura de telecomunicaciones es inherentemente geográfica: torres con coordenadas exactas, rutas de fibra que cruzan territorios, áreas de cobertura que se superponen. PostGIS nos permitió ejecutar consultas espaciales nativas — intersecciones, distancias, *buffers* — dentro de PostgreSQL sin introducir un motor geoespacial separado. Las *spatial indexes* (GIST) fueron críticas: una consulta de cobertura que tardaba 12 segundos sin índice bajó a 40 ms con un índice espacial bien diseñado.

### Microservicios por Bounded Context

Cada contexto delimitado del modelo DDD se mapeó a un microservicio independiente: Core de Telecomunicaciones, Gestión Geoespacial, Reportes, Notificaciones, y Administración. La comunicación entre servicios se centralizó en un API Gateway (NestJS) que actuó como orquestador y punto único de entrada.

### gRPC para comunicación interna

Para la comunicación entre microservicios, elegimos gRPC sobre REST. Los contratos tipados (`.proto`), la menor latencia, y la generación automática de clientes nos dieron mayor seguridad en el desarrollo y mejor rendimiento en producción. REST se mantuvo solo en el perímetro (API Gateway → clientes externos).

## Implementación clave

### Patrón Repositorio con Prisma

Uno de los desafíos técnicos más interesantes fue mantener la capa de dominio completamente pura mientras usábamos Prisma como ORM. La solución fue el patrón **Repositorio con inversión de dependencias**:

```typescript
// Domain — puerto (interfaz)
export abstract class TorreRepository {
  abstract buscarPorId(id: TorreId): Promise<Torre | null>;
  abstract buscarEnArea(centro: Coordenadas, radioKm: number): Promise<Torre[]>;
}

// Infrastructure — implementación con Prisma
@Injectable()
export class PrismaTorreRepository extends TorreRepository {
  constructor(private prisma: PrismaService) { super(); }

  async buscarPorId(id: TorreId): Promise<Torre | null> {
    const record = await this.prisma.torre.findUnique({ where: { id: id.value } });
    return record ? TorreMapper.aDominio(record) : null;
  }

  async buscarEnArea(centro: Coordenadas, radioKm: number): Promise<Torre[]> {
    const records = await this.prisma.$queryRaw`
      SELECT * FROM torres
      WHERE ST_DWithin(ubicacion, ST_MakePoint(${centro.lng}, ${centro.lat})::geography, ${radioKm * 1000})
    `;
    return records.map(TorreMapper.aDominio);
  }
}
```

El `TorreMapper` convierte entre el modelo de Prisma (plano, relacional) y la entidad de dominio (con comportamiento y reglas), manteniendo la independencia total de la capa de dominio.

### API Gateway como orquestador

El API Gateway no solo enrutaba peticiones — contenía lógica de orquestación para casos de uso que cruzaban múltiples microservicios. Por ejemplo, "registrar nueva torre" implicaba: validar datos en Core, calcular cobertura en Geo, y notificar vía WebSocket. El Gateway coordinaba esta secuencia vía gRPC, exponiendo un único endpoint REST al frontend.

## Resultados

- **Plataforma en producción** a nivel nacional para CFE TEIT, manejando operaciones críticas de telecomunicaciones.
- **Arquitectura escalable** a 5+ microservicios independientes, cada uno desplegable y escalable por separado.
- **Colaboración multidisciplinaria**: trabajo continuo con Producto, QA y DevOps durante todo el ciclo de vida.
- **Estándares técnicos**: guías de arquitectura, convenciones de código, y procesos de revisión adoptados por todo el equipo.
- **PostGIS en producción**: consultas geoespaciales con respuesta en milisegundos gracias a índices espaciales optimizados.
- **99.9% de disponibilidad** en los servicios críticos, con monitoreo y alertas automatizadas.

## Lecciones aprendidas

DDD requiere una inversión inicial significativa en entender el dominio — pero cada hora invertida en sesiones con operadores de CFE rindió frutos multiplicados durante la implementación. Sin un *Ubiquitous Language* compartido, el equipo habría construido un modelo técnico que no reflejaba la realidad operativa.

PostGIS es extraordinariamente potente, pero el diseño de índices espaciales no es trivial. Una consulta que funciona en datos de prueba puede colapsar en producción si no se diseñan los índices GIST desde el día uno. La lección: el perfil de queries geoespaciales debe hacerse antes de la puesta en producción, no después.

Clean Architecture en NestJS funciona bien, pero el costo de la indirección debe justificarse. No todos los módulos necesitan 4 capas — para lógica simple (CRUD sin reglas de negocio complejas), una arquitectura de capas reducida es perfectamente aceptable. El dogma arquitectónico sin pragmatismo genera código innecesariamente verbose.
